# AI 에이전트 루프 파이프라인 (Ralph Loop)

> spec에 정의된 객관적 기준을 100% 충족할 때까지 `구현 → 평가 → 수정`을 자동 반복하는
> 자가 검증 기반 기능 개발 파이프라인.
>
> 실제 적용 사례: [기록 뷰 전환 기능 (카드형 ↔ 리스트형)](#6-실제-적용-사례-기록-뷰-전환-기능) — 4회 루프, 기준 9/9 충족, 프로덕션 배포 완료

---

## 1. 왜 만들었나

1인 개발 환경에서 AI 코딩 도구를 쓰면서 두 가지 병목이 반복됐다.

**① "완료했다"는 선언을 믿을 수 없다.**
AI가 완료를 선언해도 타입 에러, 컨벤션 위반, 기존 기능 회귀가 섞여 있는 경우가 많아
매번 사람이 직접 빌드를 돌리고 코드를 훑어야 했다. 구현은 빨라졌는데 검증이 병목이 됐다.

**② AI는 자기 작업에 후하다.**
구현한 AI에게 "잘 됐는지 확인해봐"라고 하면 대체로 통과시킨다.
자가 채점 편향(self-grading bias) 때문에 검증의 신뢰도가 떨어진다.

→ 해법: **"AI에게 코딩을 시키는 것"이 아니라, "AI가 스스로 작업을 완수하고
품질을 증명할 때까지 돌아가는 파이프라인(환경)을 구축하는 것."**

## 2. 시스템 구성

```
AI_LOOP_GUIDE.md               # 감독관 문서 — 3-Gate 검증 기준 + 증거 보고서 양식 + 인간 개입 경계선
ralph/
  ├── README.md                # 이 문서
  ├── PROMPT.md                # 헤드리스 루프용 빌드 프롬프트 (1 iteration의 행동 규약)
  ├── IMPLEMENTATION_PLAN.md   # 루프 간 상태 공유 파일 (체크리스트 + iteration 로그)
  └── specs/
      ├── _TEMPLATE.md         # spec 템플릿
      └── {기능명}.md           # 기능별 spec — PASS/FAIL 기준표
.claude/skills/ralph/SKILL.md  # /ralph 스킬 정의 (루프 프로토콜)
scripts/ralph.sh               # 터미널 자율 루프 (최대 5회, 완료/중단 마커 감지)
```

| 구성 요소 | 역할 |
|---|---|
| **AI_LOOP_GUIDE.md** | 최상위 지침. 모든 작업 완료 선언 전 3-Gate 자가 검증과 증거 보고서 출력을 강제 |
| **spec (specs/*.md)** | 기능별 완료 기준. 주관적 표현 금지 — 객관적·이진(binary) PASS/FAIL 조건만 |
| **IMPLEMENTATION_PLAN.md** | 루프 iteration 간 공유 메모리. 체크리스트, 회차별 통과율, 실패 원인이 기록됨 |
| **PROMPT.md** | 헤드리스 모드에서 매 iteration 주입되는 행동 규약 |

## 3. 3-Gate 검증 체계

작업 완료 선언 전 반드시 순서대로 통과해야 하는 게이트.

### Gate 1 — 필수 통과 기준 (PASS or FAIL)

기술적 결함이 없는 상태를 강제한다. 전부 PASS여야 다음 게이트로 진행.

| 항목 | 명령 | 기준 |
|---|---|---|
| 타입 체크 | `npx tsc --noEmit` | 에러 0개 |
| 정적 분석 | `npm run lint` | 에러 0개 |
| 프로덕션 빌드 | `npm run build` | 성공 |
| any 금지 | `grep ": any" src/` | 신규 0개 |

### Gate 2 — 정량적 측정 기준

성능·품질 저하를 숫자로 통제한다.

| 항목 | 기준 |
|---|---|
| 번들 크기 | 직전 빌드 대비 +10% 이내 |
| 신규 의존성 | 추가 시 반드시 사유 보고 |
| 기능별 성능 | spec에 정의된 값 준수 |

### Gate 3 — 정성적 평가 기준 (1~5점)

기능만 대충 구현하고 끝내는 것을 막는다.
**점수만 적는 것 금지 — 반드시 근거(Evidence)와 수정 액션(Action)을 함께 기록.**
4점 미만이면 Action을 실행하고 재채점한다.

| 항목 | 채점 기준 |
|---|---|
| 컨벤션 일치도 | 4계층 구조, 네이밍이 기존 코드와 일치하는가 |
| 사용자 흐름 | 로딩/에러/빈 상태 처리, 예외 상황 UX가 부드러운가 |
| 상태 관리 | 전역(Zustand)과 지역(hook) 상태의 경계가 올바른가 |

## 4. 역할 분리 — 자가 채점 편향 제거

관전 모드(에이전트 팀)에서는 구현과 평가를 다른 에이전트가 맡는다.

| 역할 | 권한 | 제약 |
|---|---|---|
| **ralph-builder** | 코드 작성 | 자기 작업 채점 금지 |
| **ralph-evaluator** | 빌드·린트 실행, 기준 채점 | 코드 수정 금지 |
| **리더 (메인 세션)** | 루프 오케스트레이션, 종료 판정 | evaluator의 FAIL 리포트를 builder에게 전달 |

```
리더: builder에게 "체크리스트 항목 N 구현해" 지시
  → builder: 구현 완료 보고
  → 리더: evaluator에게 "채점해" 지시
  → evaluator: 3-Gate + spec 기준 채점 → 증거 보고서 제출
  → FAIL 있으면: builder에게 수정 지시 (루프 계속)
  → 전부 PASS면: 팀 정리 + 최종 리포트
```

이 분리는 이론이 아니라 실제로 작동했다 — [§6의 Loop 2 사건](#loop-2--역할-분리가-결함을-잡은-사건) 참고.

## 5. 안전장치

루프가 폭주하거나 위험한 변경을 임의로 진행하지 않도록 경계를 정의했다.

**인간 개입 경계선** — 아래에 해당하면 AI는 작업을 멈추고 보고 후 대기한다.

1. **데이터 스키마 변경** — Firestore 컬렉션 구조 변경, 데이터 마이그레이션
2. **보안 및 권한** — firestore.rules, Firebase Auth, 토스 본인인증 연동
3. **금전 로직** — 금액 계산 공식 등 금전적 영향이 있는 수정
4. **기획 범위 초과** — spec 범위를 넘는 대규모 리팩토링이 필요해질 때
5. **배포** — `npm run deploy` 자율 실행 절대 금지

**루프 상한** — 최대 5회 iteration. 미충족 시 중단하고 남은 FAIL 항목과 원인을 보고.

**회귀 감지** — 직전 루프에서 PASS였던 항목이 FAIL로 바뀌면 최우선 복구.

## 6. 실제 적용 사례: 기록 뷰 전환 기능

> 요구사항(자연어 입력): "지금은 캐릭터 선택창처럼 보이는 카드인데 더 깔끔하게
> 리스트카드 형태로도 선택되도록. 디폴트는 기존 카드형이고 리스트형이 선택 가능"

### 진행 과정

파이프라인이 자동으로: 코드베이스 분석 → spec 생성(PASS/FAIL 기준 9개) →
체크리스트 3개 항목 도출 → 구현/평가 루프 실행.

| Loop | 작업 내용 | 결과 |
|---|---|---|
| 1 | viewMode 상태(Zustand persist) + ViewModeToggle + MainPage 통합 | 6/6 PASS |
| 2 | RecordListItem 리스트 행 컴포넌트 + D-day 유틸 추출 | **4/6 FAIL** (lint 1 + build 2) |
| 3 | 실패 항목 수정 (미사용 변수 → 시각 강조 기능으로 연결) | 8/8 PASS (회귀 0) |
| 4 | RecordList viewMode 분기 + 리스트용 스켈레톤 | **9/9 최종 PASS** |

### Loop 2 — 역할 분리가 결함을 잡은 사건

- builder의 자가 확인: `npx tsc --noEmit` → **통과**
- evaluator의 독립 검증: `npm run build` → **실패 (에러 2건)**
- 원인: `tsc --noEmit`은 `noUnusedLocals` 검사를 적용하지 않음.
  실제 빌드의 `tsc -b`가 미사용 변수를 잡아냄
- 조치: ① 미사용 변수(isUpcoming)를 삭제하지 않고 D-day 시각 강조 기능으로 연결,
  ② 이후 builder의 자가 확인 기준을 실제 빌드 명령으로 상향

구현자가 "통과"라고 보고한 것을 평가자가 뒤집은, 역할 분리의 가치가 증명된 순간.

### 최종 결과

| 항목 | 수치 |
|---|---|
| 검증 기준 충족 | 9/9 (100%) |
| 총 루프 | 4회 (실패 1회 → 자가 복구) |
| 기존 기능 회귀 | 0건 |
| 번들 크기 증가 | +0.01% |
| 신규 의존성 | 0개 |
| 변경 규모 | 11개 파일, +582줄 |
| 배포 | 토스 앱인토스 프로덕션 |

실패에서 복구까지 사람의 개입 없이 루프 안에서 해결됐고,
전 과정이 IMPLEMENTATION_PLAN.md에 회차별로 기록되어 추적 가능하다.

## 7. 사용법

```bash
# 대화형 (단독 루프)
/ralph settlement

# 관전 모드 — tmux 분할 창에서 builder/evaluator 실시간 관전
tmux new -s ralph && claude
/ralph "기능 설명" 팀으로 돌려줘. 보면서 할래

# 헤드리스 — 터미널 자율 루프 (spec이 이미 있을 때)
./scripts/ralph.sh {기능명} [최대반복=5]
```

spec이 없으면 Phase 0에서 요구사항을 기반으로 자동 생성한 뒤 루프를 시작한다.

## 8. 배운 점

1. **AI 코딩의 생산성은 "빨리 짜는 것"이 아니라 "완료 기준의 객관화"에서 나온다.**
   모호한 요구사항을 PASS/FAIL 기준 9개로 번역하는 작업이 전체 품질을 결정했다.

2. **구현자와 평가자의 분리는 실제로 결함을 잡는다.**
   같은 모델이라도 역할과 컨텍스트를 분리하면 검증의 독립성이 생긴다.

3. **검증 도구의 한계를 아는 것도 검증의 일부다.**
   `tsc --noEmit`과 실제 빌드의 차이처럼, 기계 검증도 어떤 명령이 "진짜 게이트"인지
   루프를 돌며 교정해야 한다.

4. **상태 파일이 곧 문서다.**
   IMPLEMENTATION_PLAN.md에 남은 회차별 기록은 디버깅 로그이자
   회고 자료이자 포트폴리오의 근거 데이터가 됐다.
