# 얼마냈지 백엔드 전환 설계

- 상태 · 제안
- 작성일 · 2026-11-24

## 범위와 결정

React 토스 미니앱의 개인 기록과 빠른 장부 저장을 FastAPI + PostgreSQL로 전환한다. 인터뷰 빌드는 합성 기록과 독립 데모 계정을 사용한다. Flutter 앱은 SQLite 기반의 별도 제품이다. 운영 토스 빌드의 저장소나 사용자 계정 이전은 별도의 전환으로 다룬다.

첫 이정표는 PostgreSQL까지 연결된 기록 저장과 재조회다. Python 3.12 컨테이너에 FastAPI, Pydantic, 동기 SQLAlchemy와 psycopg를 사용하고 Alembic으로 스키마를 적용한다. 동기 DB 세션과 동기 라우트를 조합해 트랜잭션 경계를 먼저 익힌다. 현재 규모에서는 원본 SQL 집계와 배치 CLI로 시연할 수 있다.

## 데이터 모델

| 테이블 | 소유권과 제약 |
|---|---|
| users | 내부 사용자 UUID. 데모 계정은 배포 환경에서 별도로 준비하고 비밀번호 해시만 저장 |
| sessions | 불투명 세션 토큰의 해시, 사용자 FK, 만료 시각 |
| records | (owner_id, record_id) 기본 키. 유형은 nullable, 방향은 paid/received, 금액은 1~100,000,000원 정수, 행사일은 nullable DATE, 작성 시각은 TIMESTAMPTZ. 이름, 관계, 프로필 아이콘, 중요 표시 보존 |
| monthly_record_stats | 사용자·월 시작일·유형·방향별 건수와 BIGINT 합계. 통계의 미분류 유형은 별도 내부 값으로 정규화해 고유 키에 포함 |
| stats_refresh_state | 사용자별 마지막 성공 시각과 날짜 미입력 건수. 통계 적재와 같은 트랜잭션에서 갱신 |

의도한 조회는 사용자별 전체 기록과 사용자별 월 범위다. 기본 키의 owner_id 접두사로 첫 조회를 지원하고, 기간 조회에 필요한 시점에 (owner_id, event_date) 인덱스를 추가한다. createdAt은 서버가 신규 기록 생성 시 부여한다. 합계는 NUMERIC이나 부동소수점 변환 없이 정수 단위로 계산한다.

## API 계약

React와 HTTP의 JSON은 기존 MoneyRecord 필드명을 사용한다. 일반 기록의 빈 date는 저장 시 null로 바꾸고 응답 어댑터에서 빈 문자열로 복원한다. PATCH는 생략된 필드와 명시적인 null을 구분한다. 읽기 전용 ID·소유자·작성 시각은 수정 입력에 넣을 수 없다.

| 요청 | 응답 및 동작 |
|---|---|
| POST /api/v1/session, DELETE /api/v1/session | 데모 로그인 및 로그아웃. 공개 배포에서는 Secure, HttpOnly, SameSite 쿠키와 변경 요청의 Origin 검증 적용 |
| GET /api/v1/bootstrap | 현재 사용자, records, totalPaid, totalReceived를 같은 데이터 스냅샷에서 반환. 기존 검색·필터·최근 금액을 위해 데모에서는 전체 조회 |
| POST /api/v1/records | 클라이언트 생성 ID로 저장. 동일 ID·정규화된 동일 입력 재전송은 기존 결과 반환. 다른 입력으로 같은 ID를 재사용하면 409 |
| PATCH /api/v1/records/{id} | 해당 사용자 기록만 수정. 찾을 수 없으면 404 |
| DELETE /api/v1/records/{id} | 해당 사용자 기록 삭제. 반복 요청도 같은 최종 상태 반환 |
| POST /api/v1/records/batch | 받은 축의금 1~25건. 요청 내 중복 ID 거부, 기존 동일 입력 재전송 허용, 충돌 시 전체 롤백 |
| GET /api/v1/stats/monthly | 마지막 성공 배치의 월별 통계 및 갱신 시각 반환 |
| GET /healthz, GET /readyz | 프로세스 상태와 DB 접속 상태 확인 |

API는 세션에서 소유자를 얻고 SQL 조회·갱신 조건에 적용한다. 생성 충돌은 DB 고유 키로 처리한다. 모든 쓰기 응답은 저장된 기록 또는 삭제 결과와 최신 누적 합계를 반환한다. 사용자의 기록 변경이 같은 사용자 행을 잠그도록 해 변경 및 쓰기 응답의 합계 계산을 직렬화한다. UI도 HTTP 모드의 쓰기를 직렬화하고 서버 성공 응답으로 상태를 갱신해 실패나 응답 순서 역전 시 전체 스냅샷이 덮어써지는 문제를 피한다.

Zustand 초기화에서 인증·읽기·레거시 이전을 한꺼번에 수행하므로 URL 치환만으로는 부족하다. 초기화와 CRUD 인터페이스를 공통 계약으로 정리하고 빌드 설정으로 Firebase/HTTP 어댑터를 선택한다. Firestore의 레거시 이전은 기존 어댑터가 맡는다. QA에서는 일반 등록, 간편 등록, 수정·삭제, 즐겨찾기, 빠른 장부, 새로고침 후 유지까지 확인한다.

## Python 배치

1. CLI가 사용자별 잠금을 획득해 같은 사용자의 두 배치가 겹쳐 오래된 결과를 다시 적재하는 것을 막는다.
2. PostgreSQL에서 한 사용자의 원본 기록을 한 스냅샷으로 읽는다.
3. Python에서 행사일을 월 시작일로 변환하고 유형 미분류를 정규화한다. 행사일 없는 기록은 누적 합계에 포함되고 월별 통계에서는 제외된다. ID가 다르면 이름과 금액이 같더라도 각각 집계한다.
4. 사용자별 통계 삭제·재삽입과 갱신 상태 저장을 한 트랜잭션에서 커밋한다. 데이터 변환이나 적재가 실패하면 이전 성공 결과를 보존한다.
5. 처리 건수와 소요 시간만 로그에 남긴다. 대시보드 또는 Swagger에서는 마지막 적재 시각을 확인한다.

이 배치는 PostgreSQL을 입력과 출력으로 사용하는 통계 ETL이다. 여유가 생기면 합성 Firestore JSON 가져오기를 별도 CLI로 추가한다. 누락된 mode는 paid, 빈 날짜는 null로 변환한다. 원본 ID를 보존하고 유효하지 않은 행은 오류 사유와 함께 분리한다. 운영 데이터 이전을 논의할 때는 토스 식별자 검증, 사용자 매핑, 원본 및 적재 건수 대조, 부분 실패 재처리와 전환 시점의 동기화 전략이 필요하다.

## 단계별 완료 기준

| 순서 | 완료 기준 |
|---|---|
| 1. DB와 API | Compose에서 PostgreSQL 실행, Alembic 적용, Swagger로 저장 후 조회, DB 재시작 후 기록 유지 |
| 2. 기존 React 연결 | 개발 빌드에서 HTTP 모드로 일반 입력과 빠른 장부가 저장되고 수정·삭제·새로고침이 정상 동작 |
| 3. 배치 | 두 번 실행 결과 동일, 월 이동과 마지막 기록 삭제 후 이전 통계 제거, 적재 실패 시 이전 결과 보존 |
| 4. 검증 | 실제 PostgreSQL을 쓰는 Pytest로 소유자 분리, 동시 동일 ID 요청, 일괄 저장 전체 롤백, 날짜 미입력, 집계 재실행 검증. 기존 React Vitest도 실행 |
| 5. Oracle Cloud | HTTPS 접속 후 UI 저장·재조회·통계 확인, 컨테이너 재시작 후 데이터 유지, 동일 시점에 LogMe 헬스 체크 성공 |

## Oracle Cloud 병행 배포

인접 로컬 LogMe 저장소의 Compose 정의는 호스트 8000을 사용한다. Oracle 서버의 실제 포트, 프록시 종류, TLS 방식, CPU 아키텍처와 메모리·디스크 여유는 배포 전에 확인한다.

별도 디렉터리와 Compose 프로젝트 이름을 사용하고 DB 볼륨·네트워크·환경 변수·DB 계정을 분리한다. PostgreSQL 포트는 호스트에 공개하지 않는다. 호스트 프록시에서 연결한다면 사용 가능 여부를 확인한 뒤 127.0.0.1:8010 같은 포트를 사용한다. 프록시가 컨테이너라면 프록시와 웹/API만 프록시 네트워크에 연결하는 구성을 검토한다. 데모 서브도메인에서 React와 /api를 같은 출처로 제공한다.

첫 배포는 이미지 빌드, DB 기동, Alembic 적용, API 기동, 내부 readiness 확인, 프록시 설정 검증·반영, HTTPS 스모크 테스트 순으로 진행한다. 문제가 생기면 데모 라우트와 프로젝트만 내리고 DB 볼륨을 보존한다. 후속 API 버전 롤백이 필요한 경우에는 이전 이미지와 호환되는 스키마 변경을 전제로 한다.
